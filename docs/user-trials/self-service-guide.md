# TreasuryTally 用户自助操作说明

本说明面向需要验收外部服务商链上拨款报表的财务或运营人员。它描述支持范围内的通用操作，不要求使用仓库固定样例。

## 开始前准备

准备服务商提供的 CSV 或单工作表 XLSX 转账明细，也可使用符合 `UploadedReport` 格式的 UTF-8 JSON，
以及可由你确认的核验范围。不假设服务商会直接提供本系统的 JSON：

- Sepolia，`chain_id=11155111`；
- 一个 ERC-20 代币地址；
- 最多两个已确认的组织资金账户；
- 资助对象地址；
- 闭合的起止区块；
- 纳入和排除规则；
- 最多 200 条相关转账。

不要上传真实敏感报表、客户资料、密钥、助记词或生产钱包信息。系统仅支持受限 XLSX，不支持旧 XLS、PDF、截图、
任意链、任意代币语义或主网资金操作。

CSV 编码为 UTF-8（可含 BOM）或 GB18030；XLSX 必须只有一个可见工作表，无公式、宏或外部链接。
文件最多 1 MB、1–200 行明细、64 列。金额必须明确单位；XLSX 的金额及声明总额必须使用文本单元格，
不能靠转换恢复 Excel 已损失的精度。日期及其他非 General 数值格式不支持。

## 报表格式

顶层字段：

| 字段 | 要求 |
|---|---|
| `schema_version` | 固定为字符串 `"1.0"` |
| `claimed_total_base_units` | 非负十进制整数字符串；不得使用小数或科学计数法 |
| `claimed_count` | 非负整数 |
| `transfers` | 0–200 条转账记录 |

每条 `transfers` 记录必须提供：`chain_id`、`token_address`、`transaction_hash`、`log_index`、`block_number`、
`block_hash`、`from_address`、`to_address`、`amount_base_units`、`token_decimals` 和 `source`。上传报表的 `source` 必须为
`"service"`。事件身份至少由 `chain_id + transaction_hash + log_index` 共同确定。

可在页面“查看上传格式与身份说明”中查看当前 schema。不要照抄固定样例的地址、金额或区块；应把自己的测试报表映射到上述字段。

## 自助验收步骤

1. 打开集成负责人提供的 M13 合流版入口，确认页首显示预期环境；生产演示应为真实 Sepolia 只读核验。
2. 在“服务商报表”上传 CSV/XLSX 或 JSON。表格先自动转成 JSON 候选：核对列映射、金额单位、精度和完整预览。
   可补充全表链 ID、代币地址、精度；缺少交易哈希、日志序号、区块、付款/收款地址或金额时须补原表，不会自动猜填。
   已有声明总额/笔数原样保留；未提供时会标注“由明细计算”，不是服务商原声明。明确采用完整候选后才进入原上传流程。
   转换成功不代表核验通过。JSON 仍按原严格格式校验；失败时检查编码、字段、重复 key、金额、来源和上限。
3. 填写核验范围说明。用业务语言写清链、代币、资金账户、资助对象、区块范围和内部互转排除规则。
4. 生成任务候选，逐项核对结构化字段。地址外观不能证明组织归属；范围错误时先修改，不要确认。
5. 显式确认任务范围。确认后系统生成不可变任务指纹；后续不得静默改变范围。
6. 发起 Attempt 1。等待独立 RPC 证据读取和确定性核对完成；不要把加载中或提交状态当作结论。
7. 先看结论、服务商声称金额、链上有效金额和差额，再查看 Finding、资金流及对应交易/事件证据。
8. 若为 `FAIL`，根据 Finding 修正同一份报表并上传唯一一次补交；Attempt 1 必须仍可查看。
9. 若为 `INCONCLUSIVE`，先查看证据来源诊断和原因。不要据此否定服务商；按“异常恢复”处理。
10. 若为 `PASS`，只表示当前固定范围和当前证据下满足确定性规则。公开回执或写链仍需另行授权。

## 如何理解结果

- `PASS`：当前固定范围内、证据充分时，没有确认的规则违反。
- `FAIL`：至少存在一项证据充分且可复现的规则违反。
- `INCONCLUSIVE`：证据、权限、分页完整性或必要资料不足，无法可靠判断；不是负面信誉。

金额均以代币最小单位保存和比较。页面显示的本地 intake 签名不证明外部作者身份。RPC、Blockscout、服务商自报数据必须保留
各自来源，不能混为同一事实。

## 异常恢复

| 情况 | 自助处理 |
|---|---|
| 上传文件被拒绝 | 保留原文件副本；按页面错误逐项检查 schema、编码、金额、来源和上限后重新选择文件 |
| 候选范围不正确 | 不确认；返回字段编辑，修正后重新生成或确认 |
| RPC/网络/证据不完整 | 记录时间、工作区 ID 和诊断；等待服务恢复后在允许的流程内重试，不改用离线结果冒充真实证据 |
| 页面刷新或浏览器重开 | 使用同一工作区 ID 恢复；核对任务指纹和历史 attempt，避免创建重复判断 |
| 已上传任务恢复后需要补交 | 重新选择修正版 JSON 或重新转换并明确采用修正版表格；系统不应静默替换成演示服务报表 |
| 两个 attempt 已用完 | 不覆盖历史；为新的核验范围创建新任务 |
| 发布或写链失败 | 验收结论不因此改变；分别查看 `NOT_SUBMITTED`、`SUBMITTED`、`CONFIRMED` 或 `FAILED` 状态 |

## 完成自检

完成时应能回答：核验的链/代币/账户/区块是什么，任务指纹是否固定，结果属于哪一态，声称金额与链上金额关系如何，
若有 Finding，它对应哪个交易/事件；若为 PASS 且没有 Finding，应说明范围内未发现确认问题。还应理解证据不足时为什么不能下负面结论。
