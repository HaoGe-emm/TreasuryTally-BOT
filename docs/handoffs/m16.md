## 冻结 facade

公共协议为 `trust_receipt.headless.HeadlessTrustReceiptPort`：

```text
draft_task
prepare_task_confirmation
confirm_task
prepare_report_verification
verify_report
get_result
get_receipt
replay_receipt
```

确认与核验使用两阶段 challenge。准备工具只返回绑定 digest 的 `PENDING` challenge；用户必须在 MCP 之外运行交互式
`trust_receipt.headless.cli approve`。MCP 没有批准工具，也不接收 `confirmed=true` 或确认短语。消费后按 challenge 幂等返回，
重启仍可恢复。workspace 仅用不透明 handle；路径只存在于 operator 配置。

M16 已消费 attempt 状态修复 `795ddddb7f7b8d8194f7001ef45ad5fe2dce69a5`（本分支 cherry-pick `7554e9a`），在准备和消费
challenge 时使用 `M5Workflow.get_attempt_status()`。in-flight、缺失/冲突回执和状态冲突会阻塞；两个并发批准 challenge
只能有一个取得 SQLite 原子预留。M16 未修改 `app/`。

M15 联调指出 `AttemptResultView` 原缺少任务指纹。兼容修正现已增加 `spec_hash`；报表 challenge 也返回 `task_spec_hash`，其
`payload_digest` 绑定 workspace/action/content digest/task/spec/attempt。不同工作区的相同候选摘要不同，challenge 不能跨工作区
消费。M15 比较器应升级为同时核对 `workspace_handle + task_id + spec_hash`，不能放宽成 task ID 单键。
